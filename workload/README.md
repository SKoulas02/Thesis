# Workload study: the same 132 matrices on all 13 architectures

The other measurements run one matrix at a time. This one gives every architecture the
same large, mixed job: many matrix sizes at every sparsity. It reports how long each
architecture takes and how much energy it uses for the whole job. The 13 architectures are
the six single engines of `family_builds/` (4x4, 8x4, 16x3, 8x8, 4x24, 4x32) and the seven
multi-tenant builds of `multi_tenant/` (2/3/4/5 × 4x4, 2/3 × 8x4, 2 × 16x3). On a
multi-tenant build, the tenants run different matrices at the same time.

Nothing here needs a new bitstream: the tools run the existing `.xclbin` files.

## The workload

The eleven GEMV shapes of the shape sweep (`Vitis/run_shapes.py`, 512×512 up to
8192×2048 and 2048×8192) × the four sparsities 2:4, 2:8, 2:16, 2:32 × 3 copies =
**132 matrices, 195.6 M useful multiply-accumulates per pass**. The matrices are the same
for every architecture.

- **How a matrix runs.** An M×N matrix takes ceil(M / lanes) laps of the engine. Each lap
  reads N / 32 activation windows and holds each one for 32 / m cycles at 2:m. The rows past
  M in the last lap are padding: the engine computes them and they are thrown away.
- **One calculation = one activation vector.** Matrices with the same width N are chained into
  one calculation, lap after lap, and the sparsity can change between laps. Different widths
  need separate calculations, so each tenant runs one calculation per width it holds: seven
  per tenant on every architecture.
- **Who runs what** is decided before runtime, balanced by predicted time. Matrices are
  assigned longest first, each to the tenant with the least predicted work so far. A matrix's
  data stays on that tenant's HBM channels for the whole run.
- **Capacity.** All of a tenant's matrices are resident at once, and each HBM channel holds
  256 MB. The worst case is the single 4x4, which has the whole workload on two weight
  channels; it fills 73% of one. The planner refuses any plan that would not fit.

## What is here

| File | Role |
|---|---|
| `plan_workload.py` | The workload definition, the 13 architectures (build folder, `.xclbin`, clock), the balancing, the capacity check. Writes `plans/*.json`. Python 3.6, stdlib only; `run_workload.py` imports it on the server. |
| `plans/` | The plan of each architecture: every tenant's calculations, their matrices, sparsity segments, beats, laps and predicted cycles. Generated by the planner. |
| `host_workload.cpp` | The host. Every tenant runs a list of calculations in its own thread, and all tenants run at the same time. Tenant `s` drives a single-engine bitstream (compute units without the `_t<k>` suffix), so this one host runs all 13 architectures. Derived from `multi_tenant/host_sparse_multi.cpp`. |
| `run_workload.py` | Runs one architecture, either the correctness gate (`--correctness`) or the measurement. Writes the CSVs. |
| `run_all_workloads.sh` | The chain: every architecture in turn, gate then measurement, stopping at the first failure. |
| `../scripts/analysis/make_workload_csv.py` | Checks the 13 runs against the plan and builds the chart table `results/GEMV_Workload.csv` (wall time, energy, derived engine time, overhead); the same for the per-matrix run, `results/GEMV_Workload_PerMatrix.csv`. |

## How to run it (on the server)

The tools go in one folder on the server; they run inside each build folder, where the
`.xclbin` is. Copy them over (PowerShell, from the repo root):

```
ssh skoulas@coroni "mkdir -p ~/GEMV_Sparse/workload_tools"; scp workload/plan_workload.py workload/host_workload.cpp workload/run_workload.py workload/run_all_workloads.sh skoulas@coroni:~/GEMV_Sparse/workload_tools/
```

Then, on the server, inside `tmux` (with no other measurement on the card):

```
bash ~/GEMV_Sparse/workload_tools/run_all_workloads.sh              # all 13
bash ~/GEMV_Sparse/workload_tools/run_all_workloads.sh 3x8x4 4x32   # only these
bash ~/GEMV_Sparse/workload_tools/run_all_workloads.sh --check      # preflight only
bash ~/GEMV_Sparse/workload_tools/run_all_workloads.sh --per-matrix # one vector per matrix
bash ~/GEMV_Sparse/workload_tools/run_all_workloads.sh --moe        # mixture of experts
```

**MoE mode (`--moe`)**, the professor's mixture-of-experts case:
- **Workload:** one token through **7 layers, one per width** (512 … 8192). A layer holds **12 experts of every shape with that width**. For example, the width-768 layer has 12 × 768×768 and 12 × 3072×768. Each expert is a MIXED matrix (four row quarters at 2:4, 2:8, 2:16 and 2:32). All experts of a layer read the **same** token vector, so they can be stacked. That is 132 experts and 195.6 M MACs per token on every build, the same work as the other two modes.
- **Split and stacked:** in every layer the experts are split over the engines so the layer ends as early as possible (largest first, each to the least-loaded engine). Each engine **stacks its share into one calculation**, one launch per layer. The predicted engine time is the sum, over the layers, of the busiest engine's time.
- **Lockstep:** the engines wait for each other after every layer (host `--lockstep`).
- **Which builds:** the 13 builds, plus the shared-vector builds of `multi_tenant/*_shared/`. On those, the host reads **one** copy of the vector in HBM channels 0–1 (host `--shared-vector`). A shared build takes part only once its DATA_CLK is written into `SHARED_ARCHS` in `plan_workload.py`; the preflight refuses one named without it.
- **Correctness gate:** each of three test layers has 12 small experts, split and stacked by the same rule; the middle layer has two expert sizes, so the stacks are uneven. One tall matrix (every engine's stack in turn) with one vector and its golden output is cut at lap boundaries into one stack per engine. The cut is proven byte for byte before the card runs, and then every engine must be bit-exact.
- **Output:** CSVs `workload_moe_*` into `results/workload_moe/`, which become `GEMV_Workload_MoE.csv`, and `GEMV_Shared_Twins.csv` (each shared build beside its own-vector twin).

**Two modes.** Without a flag, the matrices of one width share a calculation and its input
vector: 7 calculations per engine, the run of 2026-09-25. With `--per-matrix`, every matrix
is its own calculation with its own vector, as one request per user would be (the
multi-user inference case): 132 calculations on a single engine, 26–67 per engine on the
multi-tenant builds. The balancing then adds each build's start-up cost per calculation
(measured on 2026-09-25) to every matrix's predicted time. The matrices, the host, the
checks and the measurement are the same in both modes. The per-matrix CSVs are named
`workload_permatrix_<arch>_<MHz>MHz[_calcs].csv`, belong in `results/workload_per_matrix/`,
and become `results/GEMV_Workload_PerMatrix.csv` (sheet "Workload per matrix").

The chain first runs a **preflight** over every selected architecture, and stops before the
first run if anything is wrong. It checks that:
- the build folder and `.xclbin` named in `ARCHS` exist;
- the `.xclbin` runs at the clock the plan expects (its DATA_CLK, read with `xclbinutil`);
  a mismatch means a wrong or rebuilt file;
- every name given on the command line is one of the 13.

`--check` runs only the preflight, which makes it a quick first step.

Then, for each architecture, the chain does the following:
- goes into its build folder and checks the `.xclbin` is there;
- compiles `host_workload` for the engine shape;
- copies `power_scraper.py` in if it is missing;
- runs the **correctness gate**, then the **measurement**.

It sources XRT itself and refuses to start without working power telemetry. It stops at the
first failure and says how to resume. It takes a few minutes per architecture, most of it
the soak and the idle window. The script is read whole before it starts, so copying a new
version over it during a run is safe. The log is
`~/GEMV_Sparse/workload_chain_<date>.log`. The CSVs stay in each build folder, and the last
line printed is the `scp` that brings them all home to `results/workload/`.

- **Correctness gate.** This proves the new part of the host: a tenant switching its movers
  between several calculations. Every tenant runs three small calculations with golden
  outputs:
  - widths 64, 128 and 32;
  - the sparsity changing lap by lap;
  - a different seed per tenant and per calculation.

  All must be bit-exact before anything is measured.
- **Clock.** `run_workload.py` reads the clock from the `.xclbin` again, and also stops on a
  mismatch when it is run by hand.
- **Measurement.**
  - Stimulus is generated for every calculation (0.53 to 0.59 GB per architecture) and
    checked against the plan, beat for beat.
  - All of it is loaded to the card.
  - One host call runs 3 timed passes, then a 60 s soak of whole passes in lockstep, while
    board power is sampled.
  - After the soak, idle power is sampled for 20 s with the bitstream still loaded.
  - The stimulus is deleted afterwards (`--keep` keeps it).

Back home, with the CSVs in `results/workload/`, build the chart table and the workbook
(Excel closed):

```
python scripts/analysis/make_workload_csv.py
python scripts/analysis/make_chart_xlsx.py
```

`make_workload_csv.py` writes nothing if any check fails. It needs all 13 runs, each
matching the plan calculation for calculation, and consistent energy and active time.

## What is measured

Each architecture writes `workload_<arch>_<MHz>MHz.csv` (one summary row) and
`workload_<arch>_<MHz>MHz_calcs.csv` (every calculation of every timed pass: start, the
moment its last input mover started, end, beats, laps). Every column of the summary row is
measured or taken from the plan:

| Column(s) | Meaning |
|---|---|
| `wall_pass_us`, `wall_gmac_s` | **Wall time per pass**: soak seconds / passes. Every launch, host step and the lockstep barrier between passes are included. |
| `board_load_W`, `board_idle_W`, `vccint_*` | Mean board and VCCINT power over the soak (after a 6 s warm-up) and over the idle window after it. |
| `energy_wall_uJ` (`_static`, `energy_dynamic_uJ`), `nj_per_mac_wall` | **Energy per pass**: load power × wall time. Static = idle power × wall time; dynamic = (load − idle) × wall time. Per useful MAC in the last column. |
| `active_sum_us` | The slowest tenant's sum of per-calculation active times (last input mover started → output mover done), mean of the timed passes. An upper bound on engine time, since each calculation still carries a fixed cost. |
| `makespan_us`, `host_wall_us` | One timed pass: device span (first start to last end) and host wall time. |
| `finish_balance` | Per timed pass, the earliest tenant's finish / the latest's (1.0 on a single engine). |
| `predicted_us`, `padding_pct`, `balance_planned` | From the plan: engine time at 100% efficiency, padded MACs as a share of useful ones, least-loaded / most-loaded tenant. |

## Engine time: derived, not fitted

The time the workload would take if launching were free cannot be measured directly: every
calculation is a set of kernel launches. It is **derived** in
`scripts/analysis/make_workload_csv.py` from two things:
- the plan's cycles (the slowest tenant, padding included);
- the build's steady-state efficiency, measured in the earlier campaigns on the same
  2:4/2:8/2:16/2:32 mix (`pct_of_peak` in `results/GEMV_Configurations.csv`, 98.25 to
  99.43%).

**Engine time** is those cycles / clock / efficiency, and **overhead** is wall time − engine
time. The measured active time must be at least the engine time, and the script checks it
on every build.

The first version of `run_workload.py` tried to fit engine time from this run's own
calculations. It fitted `active = a + (beats + b·laps) / f` and summed (active − a). That
does not work on this data:
- every calculation's active time carries a fixed cost of 47 to 361 µs, which varies by
  ±17 to 70 µs between calculations;
- a tenant has only seven calculation sizes;
- on 10 of the 13 builds the fit fell back to b = 1, and then the sum reduces to the plan's
  own prediction, so it measured nothing;
- a free slope comes out below 1 (faster than one beat per cycle) on most builds.

The summary CSVs of the 2026-09-25 run were therefore rewritten from their own data. The 12
columns of that estimator (`steady_*`, `lap_*`, `launch_share_pct`, `energy_steady_*`,
`nj_per_mac_steady`, `balance_measured`) were dropped, and `active_sum_us` and
`finish_balance` were added, computed from the `_calcs.csv` files. Nothing else changed,
and the original files are still in the build folders on the server.

- **On this workload the fast builds are launch-bound.** Overhead is 10% of the wall time on
  the 4x4 and 68% on the 4x32. Each tenant runs seven calculations per pass, and each one
  costs from 0.24 ms (4x4) to 0.94 ms (4x32) outside the engine.
- **Where the overhead goes** (per calculation, timed passes 2 and 3):
  - launching grows with the compute units one host thread starts: 56 to 77 µs for a 4x4
    tenant (6 movers), 364 µs for the 4x32 (32);
  - the fixed cost inside the active window grows with the movers in the whole bitstream,
    by about 10 µs per mover (±25 µs around that trend): 47 µs with 6 movers, 361 µs
    with 32;
  - the host gap to the next calculation is 51 to 91 µs (139 µs on the 4x32).
- **So replicas win on the wall clock.** A multi-tenant build pays the bitstream-wide cost
  like a large engine does, but each tenant launches only its own few movers, from its own
  thread. The five fastest builds are all replicas, within 4% of each other: 2 × 16x3,
  4 × 4x4, 5 × 4x4, 2 × 8x4, 3 × 8x4 (6.77 to 7.04 ms). The best single engines, 8x8 and
  4x24, take 8.2 ms. The largest engine, the 4x32, takes 9.65 ms, slower than the 16x3 on 13
  channels.
- **With launching free, the order is that of the steady-state measurements:** 3 × 8x4
  (2.94 ms), 2 × 16x3 (3.06 ms), 4x32 (3.08 ms).
- **Energy follows the wall time,** because static power is 88 to 94% of it. The lowest
  energy per pass is 4 × 4x4 (252 mJ, 1.29 nJ per MAC), then 2 × 8x4 (255 mJ), then 16x3 and
  2 × 16x3 (260 mJ). The 4x32 costs 342 mJ and the 4x4 467 mJ.
- **The tenants finish within 1.2% of each other on five of the seven multi-tenant builds.**
  The two lowest are 4 × 4x4 (0.963) and 5 × 4x4 (0.968). The plan balances engine time
  only, so a tenant's share of launch cost is not balanced.
- **The idle power** measured after each soak matches the earlier campaigns within 0.6 W
  on every build.

## Limits

- **Shared input vectors make this the best case for launches.** Matrices of the same width
  run in one calculation, so they are all multiplied by the same input vector. That keeps
  the launches at the minimum the engine allows: 7 per engine per pass. It is realistic when
  a few matrices really take the same input, such as the query, key and value projections of
  an attention layer. It is not realistic for 24 independent matrices, which would each have
  their own vector. Engine time does not depend on this choice; only the number of launches
  does. With one vector per matrix, a single engine would run 132 calculations per pass.
  Estimated from the measured per-calculation costs (not measured), overhead would then be
  62–97% of the time, and the small replicated engines would finish first (5 × 4x4 about
  15 ms, 4 × 4x4 about 16 ms, the 4x32 about 117 ms).
- **Static assignment.** Balancing is by predicted engine time, which ignores the launch
  cost. `finish_balance` shows how much that matters.
- **Engine time is derived, not measured here** (see above). It inherits the efficiency
  measured on each build's earlier runs, and counts the lap bubble twice: once in the plan's
  cycles and once inside that efficiency. That double count is at most 0.34% of the beats.
- **The soak runs in lockstep.** A pass ends when the slowest tenant finishes, so a tenant's
  idle tail is charged to every pass. That is the cost of running the workload repeatedly
  with a barrier between runs.
- **The 4x24's wall time is probably about 0.5 ms (7%) too high.** On the other builds the
  soak passes take 0.2 to 0.7 ms longer than the device span of the timed passes (thread
  start and join, the first set-up of each pass). On the 4x24 they take 1.05 ms longer, and
  the cause was not found. At the pace of its timed passes it would take about 7.7 ms per
  pass instead of 8.23. That moves it ahead of 8x8 and 3 × 4x4 but changes no podium place.
- **The overhead is XRT's and the host's,** measured on one server (load average 1.5 to 4
  during the runs). The breakdown above is an observation; its causes inside XRT were not
  investigated.
- **Power is sampled at about 1 Hz,** so a 60 s soak gives a steady-state mean, not a
  profile.
- **Not modelled here:** the transformer-layer workload (the alternative considered when
  this study was designed). It would chain dependent GEMVs of one model layer.
